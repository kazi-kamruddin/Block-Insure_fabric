# Session C — sealed-phase guard, sequence 4 and freeze checks

26 November 2026, Asia/Dhaka. Channel `insurance-dev-lite-190` (LevelDB, five business peers, one Raft orderer), chaincode `insurance-contract` 1.9.0. This record covers the last change before the freeze: a protocol fix found in the pre-freeze audit, its live deployment as lifecycle sequence 4, and the checks run around it. Every figure here comes from this session's logs; nothing is copied from earlier runs.

## 1. What was wrong

Every chaincode clock is the transaction proposal timestamp, accepted only within ±15 s of the endorsing peer's wall clock (`ledgerNow`, [`ledger_time.go`](../../chaincode/insurance-contract/src/ledger_time.go)). Up to sequence 3, three sealed-value entry points decided whether sealing was still open from that timestamp alone:

| Entry point | Sequence 3 gate | Reveal opens when |
| --- | --- | --- |
| `SubmitOracleCommitmentV2` (medical Oracle v2) | `now ≤ CommitDeadline` | all three committed, or `now > CommitDeadline` |
| `SubmitOracleCommitment` (legacy v1 Oracle) | `now ≤ CommitDeadline` | same rule |
| `CommitAuditorVote` (sealed panel ballot) | `now < CommitDeadline` | all four committed, or `now ≥ CommitDeadline` |

A participant that had not sealed could wait for the deadline, watch another participant reveal, and then submit a proposal timestamped up to 15 s earlier, which still looks timely. For the Oracle this means copying a public fact vector into a fresh commitment. If the two honest workers disagree, the copy becomes a false 2-of-3 majority. For the panel it breaks sealing, which exists so that no auditor can see a vote before committing their own. The gap existed in REAL timing as well as DEMO; DEMO only made it obvious, because 15 s is the entire DEMO Oracle commit window.

Exposure differed by role. Oracle workers hold their own enrolled identities, so a compromised worker operator could craft timestamps. Auditor identities stay behind the server-side Gateway, which sets proposal timestamps, so a browser user could not exploit the ballot gap without the Gateway itself being compromised.

## 2. The fix

All three entry points now also refuse once the first reveal exists in ledger state:

- Oracle v2 and v1: refuse when `request.RevealCount > 0` (error `commit phase has ended`).
- Sealed ballots: refuse when `review.VotesCast > 0` (error `panel commitment deadline has elapsed`).

No new state field or schema change was needed. Each commit already reads and rewrites the same request or review key that a reveal rewrites (`CommitmentCount++`, `CommitmentsCast++`). Fabric's MVCC validation therefore serialises a racing commit and reveal: if both read the same version, only the first ordered one is valid. The first reveal thus acts as the stage switch that the TLA+ models represent with a single `stage` variable, and the implementation can no longer admit a sealed value after any value is open.

The clock tolerance remains, and it now affects liveness only. A forward-dated reveal can start the reveal phase up to 15 s early. A slow honest participant may then be shut out and count as absent. Exact 2-of-3 Oracle agreement and the 3/2/4 panel thresholds still decide, so which values count is unchanged.

Source: [`oracle_v2.go`](../../chaincode/insurance-contract/src/oracle_v2.go), [`oracle.go`](../../chaincode/insurance-contract/src/oracle.go), [`medical_sealed_votes.go`](../../chaincode/insurance-contract/src/medical_sealed_votes.go). Design note: [R2 design, phase order](../oracle-v2/R2-DESIGN.md#phase-order-under-clock-tolerance-sequence-4).

## 3. Tests

[`late_commit_guard_test.go`](../../chaincode/insurance-contract/src/late_commit_guard_test.go) reproduces the attack directly. The mock peer clock is set 10 s past the deadline, and the proposal timestamp 1 s before it, which `ledgerNow` accepts:

| Test | Scenario | Sequence-3 source | Sequence-4 source |
| --- | --- | --- | --- |
| `TestOracleV2FirstRevealClosesCommitPhase` | Two commit, deadline passes, one reveals, the silent third copies the public vector with a backdated commitment. The honest second reveal must still finalize. | **FAIL**: late commitment accepted | PASS: refused; 2 commitments, 2 reveals, `PANEL_REVIEW` |
| `TestOracleV1FirstRevealClosesCommitPhase` | Same attack on the legacy v1 path | **FAIL** | PASS |
| `TestSealedPanelFirstRevealClosesSealing` | One auditor seals and reveals REJECT, a second seals a matching ballot with a backdated proposal | **FAIL** | PASS: refused; review unchanged |
| `TestOracleV2ToleratedCommitBeforeAnyRevealStillCounts` | A backdated commitment before any reveal is still accepted, showing that the guard is state-based and that ordinary skew stays tolerated | PASS | PASS |

The mutation check (sequence-3 source restored temporarily, then the fix put back) is the evidence that the tests detect the defect rather than pass trivially.

[`medical_audit_escalation_test.go`](../../chaincode/insurance-contract/src/medical_audit_escalation_test.go) adds the claimant branch of audit sampling, which previously had no test. A claim held in `MEDICAL_AUDIT_PENDING`, in a period whose Insurer and Hospital shares were never revealed, cannot be escalated before the grace deadline. After `AUDIT_SEED_DEFAULTED` it escalates into panel preparation exactly once.

## 5. Live U13 check: altered disclosure bytes

`.project-context/implementation/session-c/u13-probe.mjs` (local, git-ignored) used the Insurer Gateway identity and **evaluate only**, so nothing could be ordered or written. Against `CLM-2026-SESSION-A-K2`, private facts of 476 and 512 bytes were read; only their lengths and digests were printed.

| Transient input to `PrepareMedicalReview` | Live peer result |
| --- | --- |
| Exact episode and statement bytes | Accepted in simulation: `PREPARING`, disclosure issued |
| Episode with one bit flipped | Refused: `transient facts do not match the committed medical record` |
| Statement with one bit flipped | Refused: same message |

The comparison is a constant-time check of the SHA-256 of the supplied bytes against the private-data hash already on the ledger. The live peer, not a unit-test stub, refused a one-bit change.

## 6. Interface and tooling changes

- **Status badge.** `ORACLE_FAILED` now reads **Oracle did not auto-approve** in the pending tone. The chaincode uses this status whenever the Oracles do not auto-approve, including an agreed referral to the panel, so a red "failed" badge misdescribed a normal routing outcome. The ledger value is unchanged. Test: `apps/web/components/status-badge.test.tsx`.
- **Audit resolver.** The Insurer's **Medical audit sampling** card now has **Held claim ID** and **Resolve audit selection**, which call the existing `resolve` API action. Previously that step needed a service-side call. Test: `apps/web/components/medical-audit-period.test.tsx`.
- **Launcher.** `scripts/r2-demo.ps1` recreates a *stopped* ccaas container whose package ID predates an upgrade; it still refuses to touch a running one. The container has no volumes, only the read-only binary mount.
- **Preflight.** The R2 backup check recognises `*-pre-seq*` backups.
- **Ignore policy.** `/data/`, `/backups/` and backup tarballs are now ignored as a whole. No file under `data/` was tracked.

## 8. What this does not show

- No new Oracle round or panel vote ran live on sequence 4. Memory after the read-only start was about 650 MB, below the 700 MB business-write floor. The honest-path behaviour is covered by the Go suite. The first live claim on sequence 4 is the owner's hands-on run.
- The guard was not exercised by a live malicious worker; that requires a hand-crafted backdated proposal, which the Go tests reproduce instead.
- During the session Docker Desktop's WSL engine stopped once on its own while drive C had about 0.2 GB free. It came back without intervention, and all six ledger volumes were present afterwards. Keep more free space on C before demonstrations.
