## Fabric mechanisms

Insurer administrators and Oracle roles can read it; another hospital subject and policyholders cannot. Corrections follow the existing void/new-invoice policy. No private diagnosis or expected range is added to public ledger values.

When `FABRIC_XGBOOST_ENABLED=true` in an isolated candidate environment, registry publication gathers those private facts and commits their canonical context hash into the registry root. Missing facts remain explicit. Requests select the generated Fabric evaluator identity and preserve the existing three Oracle / exact two-result quorum. The flag is deliberately unset for preserved legacy environments until the candidate passes live verification and an activation plan is reviewed.

Context-bearing snapshots require a shared server/worker `ORACLE_REGISTRY_API_TOKEN` of at least 32 characters; they return `Cache-Control: no-store` and reject anonymous access. Configure the same token in the web server and each worker, never frontend variables. Historical snapshots without model context retain their existing public behavior. Snapshot JSON, worker decisions and credentials remain local under ignored state roots.

Registry integrity, patient/source authorization and selective-disclosure checks run before model routing. `XGB_AUTO:<digest>` and `XGB_REVIEW:<digest>` bind the complete model assessment/context to existing commit/reveal result hashing. Unavailable context routes away from automatic approval. Chaincode validates the version-specific result form; it does not execute nondeterministic inference. Legacy `model-v1` requests keep their fixed-code validator. Human adjudication and Bank settlement remain independent authorities.

Before commitment the worker durably stores an authenticated, deployment-qualified decision. A restart uses that decision even if source retrieval is unavailable. An existing commitment without its saved decision fails closed; restore the correct state backup rather than recomputing from live data or deleting a checkpoint. Enrolled key/certificate rotation during an in-flight request requires preserving the old authorized worker state; it is not an automatic migration.

For historical `model-v1` commitments created before this journal existed, the worker may adopt a recomputed legacy decision only if its complete commitment hash exactly reproduces the ledger commitment. A different hash is rejected; this exception does not apply to new XGBoost requests.

## Payment and evidence recovery changes

Manual premium OTPs now bind the recipient and exact payment IDs, accounts, period, amount and external reference. Protected challenge state and attempt counts persist under `OTP_STATE_ROOT` (default data/otp, qualified by channel), with cross-process exclusion. Replacements invalidate older challenges; failed delivery revokes the new challenge. A valid OTP authorizes an attempt, not settlement. Keep the same authentication/OTP secret while outstanding challenges exist; changing it makes old protected state unreadable. Do not delete challenge state to bypass attempt or replay controls.

Before sending a manual payment, the browser saves its original intent without the OTP. **Recover saved payment** reads authoritative transfer and premium linkage for that intent. A valid linked SETTLED result or a BOUNCED transfer is terminal; missing/unknown state remains unresolved. This is not a replacement for recording Fabric commit validation codes in live evidence. No recovery action should invent new payment/transfer IDs for an uncertain operation.

Evidence upload now retains ciphertext on uncertain ledger outcomes. Retrying the same bytes/identifiers can recover exact committed linkage; different existing bytes are rejected. Version-pinned registration prevents a claim-version change between preparation and endorsement from silently attaching evidence to another version. Unresolved linkage is explicitly pending, not verified.

An optional **separate backup password** creates a downloadable `.bifkey` recovery file using existing BIF1 authenticated encryption. Keep that file and password separately; either the original content passphrase or both recovery components are needed. Restore the key in the retrieval form, then fetch and verify the original ciphertext. No server-held certificate signature is presented as user-exclusive custody. Per-document secret sharing with authorized reviewers remains an explicit owner action; grant records alone cannot decrypt files. The backup does not widen access, back up the ciphertext, or revoke secrets already learned by a reviewer.
